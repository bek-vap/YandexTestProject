# Яндекс.Отзывы

Это моё тестовое. Вставляешь ссылку на организацию в Яндекс.Картах, и приложение
показывает её отзывы, средний рейтинг и счётчики. Дело в том что у Яндекса нет
открытого API, поэтому всё приходится доставать парсингом. Это была самая сложная и
самая интересная часть.

Стек: Laravel 13 на бэке, Vue 3 на фронте (SPA, Composition API). Авторизация через
Sanctum по кукам. База MySQL на сервере и SQLite локально. Парсинг через Playwright,
это headless-браузер. Парсинг идёт в фоне через очередь.

## Что умеет

- вход по логину и паролю (пользователь один, регистрации нет)
- страница настроек: вставляешь ссылку, она проверяется и сохраняется
- парсинг идёт в фоне, статус видно на странице
- отзывы по 50 на страницу, у каждого автор, дата, текст и оценка
- средний рейтинг, число оценок и число отзывов отдельно

Логин: admin@example.com, пароль: password

Про демо. Я развернул проект на своём VPS, у него 1 CPU и 2 ГБ памяти. Браузеру на
таком сервере не хватает памяти, чтобы собрать все 600 отзывов. Я конечно долго с этим
возился, но стабильно проходит около 100. Ну и поэтому на демо стоит лимит
YANDEX_REVIEW_LIMIT=100. Рейтинг и счётчики при этом настоящие, я беру их прямо со
страницы Яндекса. Поэтому счётчик показывает полное число (например 2719), а в списке
столько, сколько успел собрать. На сервере помощнее лимит просто убирается.

## Как запустить через docker-compose

Нужен только Docker.

```
docker compose up --build
```

Поднимутся три контейнера: база, приложение и воркер очереди. Потом открываешь
http://localhost:8000 и заходишь под логином выше. Первый запуск долгий, потому что
качается Chromium.

## Как запустить без Docker

Нужны PHP 8.2+, Composer и Node 20+.

```
composer install
npm install
npx playwright install chromium
cp .env.example .env
php artisan key:generate
php artisan migrate --seed
```

Дальше в трёх терминалах:

```
php artisan serve
npm run dev
php artisan queue:work
```

## Переменные окружения

- QUEUE_CONNECTION: database (очередь через таблицу jobs)
- YANDEX_REVIEW_LIMIT: сколько отзывов тянуть, если пусто то все
- SANCTUM_STATEFUL_DOMAINS: домен фронта, без него не работает авторизация по кукам
- DB_*: подключение к базе

## База данных

- users: пользователи
- organizations: карточки организаций (ссылка, название, рейтинг, счётчики, статус)
- reviews: отзывы (id отзыва на Яндексе, автор, оценка, текст, дата)
- organization_snapshots: снимки цифр после каждого парсинга, для истории

У пользователя может быть много организаций, у организации много отзывов и снимков.
Одну и ту же ссылку пользователь два раза добавить не может, и один отзыв у организации
тоже не может лежать два раза.

## Как это работает

1. Пользователь сохраняет ссылку. Контроллер её проверяет, ставит задачу в очередь и
   сразу отвечает, чтобы человек не ждал.
2. Воркер берёт задачу и вызывает сервис YandexReviewsParser. Он запускает мой скрипт
   scripts/yandex-parser/parse.mjs, в котором и работает браузер.
3. Сервис OrganizationImporter сохраняет организацию и отзывы в базу и делает снимок.
4. Фронт каждые три секунды спрашивает статус и показывает результат, когда всё готово.

Всю логику парсинга я вынес в сервисы (папка app/Services/Yandex), в контроллере её нет.

## Как я парсил и обходил защиту

Сначала я открыл DevTools и посмотрел, как Яндекс сам грузит отзывы. Оказалось, что они
приходят запросом /maps/api/business/fetchReviews по 50 штук. А рейтинг и счётчики лежат
прямо в HTML страницы.

Я хотел просто дёргать этот запрос из PHP, но не вышло. Дело в том что запрос подписан
параметром s, а его считает JavaScript Яндекса. Плюс токен привязан к живой сессии
браузера и живёт секунд 15-30. Без настоящего браузера приходит ошибка 400. Это и есть их
защита от ботов.

Поэтому я взял headless-браузер. Настоящий Chromium сам проходит защиту и сам
подписывает запросы, а я просто забираю данные. Первую страницу и цифры беру из HTML, а
остальные страницы перехватываю, пока браузер листает. Дубли убираю по id отзыва.

Если сравнить:
- запросы напрямую быстрее и легче, но ломаются из-за подписи s
- браузер тяжелее и медленнее, зато стабильно проходит защиту и даёт те же данные

Честно, лучше всего было бы вообще не парсить, а брать данные через официальный или
платный API, если есть бюджет.

## Ответы на дополнительные пункты

1. Смена разметки. Парсер не отдаёт пустоту молча. Скрипт возвращает коды ошибок
(captcha, reviews_not_found, page_load_failed), а сервис превращает их в исключение
YandexParserException. Если на странице нет ни отзывов, ни рейтинга, значит Яндекс
поменял вёрстку. Тогда у задачи статус failed, и текст ошибки видно на сайте и в логах.
Старые отзывы при этом не удаляются.

2. Почему браузер. Прямые запросы блокируются подписью s и токеном, а браузер проходит
защиту сам. Плюс в надёжности, минус в том, что он тяжелее и зависит от вёрстки.

3. Масштаб. Парсинг идёт через очередь. Если подключат 50 филиалов, просто встанет 50
задач, и сайт тормозить не будет. При сбое задача пробует ещё раз, всего три попытки с
паузами 10, 30 и 60 секунд. Статусы pending, parsing, done и failed видно на фронте.

4. Защита от бана. Сейчас есть настоящий браузер с обычным User-Agent и лимит на объём.
А так я бы добавил паузы между организациями, ротацию прокси и User-Agent, и если
прилетела капча, повторял бы попытку с паузами всё дольше. Ну и парсил бы по расписанию,
а не на каждый клик.

5. Дубли и история. Если спарсить ещё раз, дублей не будет. Отзывы сохраняются через
upsert по паре организация и id отзыва, так что старый отзыв просто обновляется. Я это
проверял, запускал парсинг несколько раз, количество отзывов не менялось. Для истории
после каждого парсинга сохраняется снимок цифр. Если сравнить два снимка, видно что
поменялось.

## Как собрать все 600 и как масштабировать

Почему 600 не влезает. Чтобы дойти до 600-го отзыва, браузер листает страницу с самого
начала и держит всё, что загрузил, в памяти. Выкинуть это нельзя, иначе прокрутка
перестаёт работать. Я пробовал swap, флаги браузера, блокировку картинок и урезал память
MySQL. Каждое немного помогало. Вручную 600 собирались, а через очередь уже нет, потому
что там одновременно работают база и сайт.

Как бы я сделал нормально. Браузер нужен только чтобы получить живую сессию и токен. А
отзывы можно тянуть обычными запросами fetchReviews по страницам, без прокрутки. Тогда
памяти почти не нужно, и 600 влезут даже в 2 ГБ.

Проблема тут в подписи s, она своя для каждой страницы. Поэтому если перехватить один
запрос, для других страниц он не подойдёт. Разгадывать их алгоритм долго, и после
каждого обновления Яндекса он будет ломаться. Лучше найти их функцию подписи в их же
JavaScript и просто вызывать её. Если Яндекс её поменяет, придётся только найти её заново.

Ещё можно сделать самовосстановление. Работаем быстрыми запросами, а если пришла ошибка
400, значит что-то поменялось. Тогда сами запускаем браузер, берём новую сессию и токен
и работаем дальше. Тяжёлый браузер включается только когда что-то сломалось.

И не надо каждый раз тянуть всё. Отзывы идут по дате, поэтому при обновлении можно
листать только до первого отзыва, который уже есть в базе. Вместо 600 будет пара десятков
новых.

Если подключат сеть на 50 и больше филиалов:
- вынести парсинг на отдельные сервера, чтобы браузер не мешал сайту
- запускать несколько воркеров сразу, но браузер ест около 500 МБ, это надо учитывать
- парсить ночью по расписанию и не все организации разом
- не долбить с одного IP, иначе дадут капчу или бан, поэтому паузы и прокси
- если прилетела капча, не повторять сразу, а ждать всё дольше
- следить за статусами: если разом падает много задач, значит нас забанили или Яндекс
  что-то поменял

## Что бы доделал, будь больше времени

- гибридный парсинг: браузер только за сессией, отзывы запросами без прокрутки
- прогресс парсинга в реальном времени
- ротацию прокси и User-Agent
- страницу с историей изменений
- тесты для парсера и API
- нормальный веб-сервер (nginx + php-fpm) вместо artisan serve
