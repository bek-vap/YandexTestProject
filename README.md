# Яндекс.Отзывы

Приложение, которое по ссылке на организацию в Яндекс.Картах показывает её отзывы,
рейтинг и счётчики. Официального API у Яндекса нет, поэтому данные собираются парсингом.

Стек: Laravel 13 (API), Vue 3 + Vite (SPA, Composition API), Sanctum (авторизация по
кукам), MySQL в проде или SQLite локально, Playwright (headless-браузер для парсинга),
очередь на базе БД.

## Что умеет

- вход по логину/паролю (один сид-пользователь, регистрации нет)
- страница настроек: вставить ссылку, валидация, сохранение
- парсинг в фоне со статусом (в очереди / парсим / готово / ошибка)
- вывод: средний рейтинг, число оценок и отзывов отдельно, отзывы по 50 на страницу
  (автор, дата, текст, оценка)

Сид-пользователь: admin@example.com / password

Про демо-сервер: развёрнут на VPS 1 CPU / 2 GB. Чтобы браузер стабильно работал в такой
памяти, на демо стоит лимит YANDEX_REVIEW_LIMIT=100 (отзывы кэшируются в БД, показываются
по 50 на страницу). Рейтинг и счётчики реальные (читаются с Яндекса), поэтому счётчик
показывает полное число (например 2719), а список — сколько успели спарсить. Парсер умеет
собрать все ~600, на сервере с большей памятью лимит убирается (пустое значение = тянуть все).

## Запуск через docker-compose

Нужен Docker.

```
docker compose up --build
```

Поднимутся три контейнера: база (MySQL), приложение (миграции + сервер) и воркер очереди.
Потом открыть http://localhost:8000 и войти сид-пользователем. Первый запуск собирается
несколько минут — качается Chromium.

## Запуск локально без Docker

Нужны PHP 8.2+, Composer, Node 20+.

```
composer install
npm install
npx playwright install chromium
cp .env.example .env
php artisan key:generate
php artisan migrate --seed
```

Дальше в трёх терминалах:

```
php artisan serve
npm run dev
php artisan queue:work
```

## Переменные окружения

- QUEUE_CONNECTION — database (очередь через таблицу jobs)
- YANDEX_REVIEW_LIMIT — сколько отзывов тянуть, пусто = все ~600
- SANCTUM_STATEFUL_DOMAINS — домен фронта, чтобы работала авторизация по кукам
- DB_* — подключение к базе

## Структура БД

- users — пользователи
- organizations — карточки: yandex_url, name, rating, ratings_count, reviews_count,
  status, parsed_at. Уникальность по паре (user_id, yandex_url)
- reviews — отзывы: external_id (id отзыва у Яндекса), author, rating, text, review_date.
  Уникальность по паре (organization_id, external_id)
- organization_snapshots — снимки цифр на момент парсинга (история изменений)

Связи: users 1—* organizations 1—* reviews, organizations 1—* snapshots.

## Как идут данные

1. Юзер сохраняет ссылку — контроллер валидирует, кладёт задачу ParseOrganizationJob в
   очередь и сразу отвечает (не ждёт парсинг).
2. Воркер берёт задачу, вызывает сервис YandexReviewsParser, который запускает Node-скрипт
   scripts/yandex-parser/parse.mjs (headless-браузер).
3. OrganizationImporter сохраняет организацию и отзывы в БД и делает снимок.
4. Фронт опрашивает статус и показывает результат, когда готово.

Логика парсинга вынесена в сервисы (app/Services/Yandex), а не в контроллер.

## Про парсинг и обход защиты

Смотрел через DevTools, как Яндекс грузит отзывы. Отзывы приходят внутренним запросом
GET /maps/api/business/fetchReviews (постранично, page/pageSize=50), а рейтинг и счётчики
лежат в HTML страницы (ratingData и микроразметка schema.org).

Пробовал дёргать этот JSON напрямую из PHP — не выходит: запрос подписан параметром s
(его считает JS Яндекса), а токен csrfToken привязан к живой сессии браузера и живёт
~15-30 секунд. Без настоящего браузера приходит 400 Bad Request. Это и есть защита от ботов.

Поэтому взял headless-браузер (Playwright): настоящий Chromium сам проходит защиту и
подписывает запросы. Первую страницу отзывов и агрегаты (рейтинг, счётчики) беру из HTML,
остальные страницы — перехватываю JSON fetchReviews при автопрокрутке. Дубли убираю по
reviewId.

Коротко про два подхода:
- прямой JSON — быстрее и легче, но ломается из-за подписи s, очень хрупкий;
- headless — тяжелее и медленнее, но стабильно проходит защиту, данные те же.

Идеально в проде — вообще не парсить, а брать данные по официальному/платному API, если
есть бюджет.

## Ответы по дополнительным требованиям

1. Устойчивость к смене разметки. Парсер не отдаёт молча пустоту. Node-скрипт возвращает
коды ошибок (captcha, reviews_not_found, page_load_failed), сервис превращает их в
исключение YandexParserException. Если на странице нет ни встроенных отзывов, ни
микроразметки рейтинга — значит вёрстка поменялась, задача помечается failed с текстом
ошибки (видно в интерфейсе и в логах).

2. Обоснование подхода. Описано выше: взял headless, потому что прямой разбор JSON
блокируется подписью s и привязкой токена к живой сессии. Плюс headless — надёжность и
те же чистые данные, минус — тяжелее и чувствителен к смене вёрстки.

3. Масштаб и фоновая обработка. Парсинг вынесен в очередь (ParseOrganizationJob, драйвер
database). Для сети из ~50 филиалов ставится 50 задач, воркеры разбирают по одной, веб не
блокируется. Есть повторные попытки (tries=3) с нарастающими паузами (backoff 10/30/60
сек), таймаут задачи и статусы pending/parsing/done/failed, которые фронт опрашивает.
Детальный прогресс (сколько отзывов уже собрано) можно добавить, обновляя поле по ходу.

4. Анти-бан на объёме. Частично сделано, остальное — план: настоящий браузер с реальным
User-Agent, ограничение объёма за один заход (YANDEX_REVIEW_LIMIT). Дальше добавил бы
троттлинг между организациями, бэкофф при ошибках, ротацию прокси и User-Agent, обработку
бана (при капче отложить задачу и повторить позже с другого IP), и парсинг по расписанию
редко, а не на каждый клик — данные отдаём из кэша в БД.

5. Идемпотентность и история. Повторный парсинг не плодит дубли: отзывы пишутся через
upsert по паре (organization_id, external_id), существующий обновляется. Организация
обновляется, а не пересоздаётся. Для истории на каждый парсинг создаётся запись в
organization_snapshots со снимком цифр (рейтинг, счётчики) — сравнив соседние снимки, видно
что изменилось. Показ дифа в интерфейсе — следующий шаг.

## Что доделал бы с большим временем

- детальный прогресс парсинга (сколько отзывов собрано в реальном времени)
- ротация прокси/User-Agent и троттлинг для безопасного парсинга многих карточек
- экран истории изменений (диф снимков было → стало)
- тесты (сервис парсера с моками, API-тесты)
- нормальный веб-сервер (nginx + php-fpm) вместо artisan serve
